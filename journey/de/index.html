Praxis-Tipps für den Einstieg

  • Einen Screenreader richtig lernen, nicht drei halb Plattform: Linux und Windows

    Unter Windows ist NVDA kostenlos und ein guter Start, unter Linux mit Desktop Orca (in GNOME an und aus mit Super+Alt+S). Die Kürzel, die man zuerst wirklich können sollte, sind in Web und Anwendungen fast überall gleich:

    • H nächste Überschrift, D nächster Bereich (Landmark), F nächstes Formularfeld, K nächster Link
    • NVDA+F7 Elementliste: alle Überschriften, Links und Landmarks auf einen Blick
    • NVDA+Leertaste wechselt zwischen Lese- und Fokusmodus – das ist der häufigste Grund, warum „die Tasten plötzlich nicht mehr gehen“

    Warum: Wer die Navigation über Struktur beherrscht, ist schneller als jeder, der sich Zeile für Zeile durch eine Seite hört.

  • Sprechtempo schrittweise erhöhen Plattform: Windows

    In NVDA öffnet NVDA+Strg+Pfeil links/rechts den Einstellungsring der Sprachausgabe (Geschwindigkeit, Tonhöhe, Lautstärke …), NVDA+Strg+Pfeil hoch/runter ändert den gewählten Wert.

    Erhöhe die Geschwindigkeit in kleinen Schritten, etwa alle ein bis zwei Wochen, sobald sich das aktuelle Tempo normal anfühlt. Ein hohes Tempo spart beim Lesen von Code und Logs jeden Tag viel Zeit.

    Warum: Zu schnell zu früh führt dazu, dass man mehr zurückspult als liest.

  • Braillezeile für Code: Zeichen, die Sprache verschluckt Plattform: Linux und Windows

    Sprachausgabe ist schnell, aber bei Code ungenau: Klammern, Semikolons und Einrückung gehen leicht unter. Eine Braillezeile mit 8-Punkt-Computerbraille zeigt jedes Zeichen genau so, wie es in der Datei steht.

    • Für Überblick und Fließtext: Sprache
    • Für die eine Zeile mit dem Syntaxfehler: Braille
    • Stelle die Satzzeichen-Ansage für Code-Arbeit auf „alle“, damit auch Sprache Klammern vorliest
  • Erste C-Programme: immer nur den ersten Fehler lesen Plattform: Linux und Windows

    Ein einziger fehlender Strichpunkt erzeugt oft zwanzig Folgefehler. Mit Screenreader ist das besonders mühsam. Lass dir deshalb nur die ersten Zeilen ausgeben, korrigiere, kompiliere neu. 

    gcc -Wall -Wextra -o hallo hallo.c 2>&1 | head -n 5

    Die Meldung beginnt mit datei:zeile:spalte. Mit Zeilennummer springst du im Editor direkt hin, statt zu suchen.

2021 – 2022 · Ausbildung am DKFZ

1. Lehrjahr: Terminal, SQL und die Grundlagen

Am Deutschen Krebsforschungszentrum (DKFZ) in Heidelberg habe ich eine inklusive Ausbildung zum Fachinformatiker für Anwendungsentwicklung begonnen, die Berufsschule war die Hubert-Sternberg-Schule in Wiesloch. Das erste Jahr in der Abteilung Federated Information Systems drehte sich um die Grundlagen: verteilte Systeme, medizinische Informatik, Java, APIs, Docker, Linux-Konfiguration, Git, Datenbanken und Scrum.

Hier habe ich gelernt, dass das Terminal für blinde Entwickler kein Notbehelf ist, sondern das zugänglichste Werkzeug überhaupt – wenn man die Ausgabe in eine lesbare Form bringt.

Praxis-Tipps: Terminal und Datenbanken

  • Linux-Terminal: Ausgabe in Häppchen statt als Wand Plattform: Linux

    Lange Ausgaben rauschen am Screenreader vorbei. Diese Muster halten sie lesbar:

    ls -1                      # eine Datei pro Zeile
ls -1 | wc -l              # erst zählen, dann entscheiden
befehl | head -n 20        # nur der Anfang
befehl | less              # seitenweise, mit /suche
befehl > ausgabe.txt 2>&1  # in Datei, dann im Editor lesen
cd -                       # zurück ins vorige Verzeichnis

    Warum: Eine Datei im Editor kann ich zeilenweise, mit Suche und in Ruhe lesen – eine scrollende Ausgabe nicht.

  • Windows Terminal und PowerShell lesbar machen Plattform: Windows

    Windows Terminal funktioniert gut mit NVDA. Mit Strg+Umschalt+F durchsuchst du die Ausgabe, mit der NVDA-Leseansicht (Ziffernblock 7 8 9) gehst du Zeile für Zeile zurück. PowerShell gibt standardmäßig breite Tabellen aus – untereinander ist für Sprache viel angenehmer: 

    Get-ChildItem | Select-Object -ExpandProperty Name
Get-Process code | Format-List Name, Id, CPU
Get-Content .\app.log -Tail 20
Get-ChildItem | Out-File liste.txt   # in Datei lesen
Get-Location | Set-Clipboard         # in die Zwischenablage

    In der klassischen Eingabeaufforderung liefert dir /b nur die Namen.

  • SQL im Terminal: Datensätze untereinander statt Tabelle Plattform: Linux und Windows

    Eine breite Ergebnistabelle wird vorgelesen als „Strich Strich Plus Strich …“. Alle gängigen Kommandozeilen-Clients können Datensätze stattdessen als Spalte = Wert untereinander ausgeben: 

    -- SQLite (sqlite3)
.headers on
.mode line
SELECT * FROM bewerbung LIMIT 3;

-- PostgreSQL (psql)
\x auto
\pset pager off
SELECT * FROM bewerbung LIMIT 3;

-- MySQL / MariaDB: Abfrage mit \G statt ; beenden
SELECT * FROM bewerbung LIMIT 3\G

    Für Skripte und schnelle Zählungen ohne Rahmen und Kopfzeile:

    psql -d app -A -t -F ';' -c "SELECT status, count(*) FROM bewerbung GROUP BY status"

    Warum: Immer zuerst count(*) oder LIMIT – tausend Zeilen anzuhören ist keine Datenanalyse.

  • Git ohne Pager und mit kurzer Ausgabe Plattform: Linux und Windows

    Git öffnet Logs und Diffs in einem Pager, der für Screenreader oft schwer zu verlassen ist. Kurze Formate helfen sofort: 

    git status -s
git --no-pager log --oneline -n 10
git diff --stat
git diff --word-diff   # zeigt, welches Wort sich geändert hat, nicht nur die Zeile

    Wer den Pager gar nicht will: git config --global core.pager cat.

  • Docker-Ausgaben auf das Wesentliche kürzen Plattform: Linux und Windows

    docker ps liefert eine sehr breite Tabelle. Mit --format bekommst du genau die Felder, die du brauchst:

    docker ps --format '{{.Names}}: {{.Status}}'

    Ergebnis zum Beispiel: db: Up 2 hours – eine Zeile pro Container, sofort verständlich.

2022 – 2023 · Krebsinformationsdienst

2. Lehrjahr: Webentwicklung

Im zweiten Jahr war ich beim Krebsinformationsdienst und habe mit PHP und JavaScript an einer Online-Beratungsplattform mitgearbeitet. Das war meine erste Arbeit an Oberflächen, die andere Menschen benutzen – und die beste Schule dafür, Barrierefreiheit von der anderen Seite zu sehen.

Praxis-Tipps: Web und APIs

  • Eigene Seiten mit dem Screenreader in drei Schritten testen Plattform: Linux und Windows
    1. Überschriften: Mit H durchspringen. Ergibt die Liste allein ein sinnvolles Inhaltsverzeichnis?
    2. Bereiche: Mit D durch die Landmarks. Gibt es header, nav, main, footer?
    3. Formulare: Mit Tab durch alle Felder. Wird zu jedem Feld eine Beschriftung vorgelesen, nicht nur „Eingabefeld“?

    Warum: Diese drei Prüfungen finden in wenigen Minuten die meisten Probleme, lange bevor ein Audit-Tool läuft.

  • APIs mit curl und jq statt im Browser lesen Plattform: Linux und Windows

    JSON im Browser ist mit Screenreader oft ein einziger langer Absatz. Im Terminal formatiert jq die Antwort und filtert genau das heraus, was du brauchst: 

    curl -s https://api.example.org/jobs | jq '.'
curl -s https://api.example.org/jobs | jq -r '.items[].title'
curl -s https://api.example.org/jobs | jq '.items | length'

    Unter Windows gibt es curl.exe und jq ebenfalls, zum Beispiel über winget install jqlang.jq.

  • Browser-Konsole statt visueller Entwicklertools Plattform: Linux und Windows

    Die visuellen Teile der Entwicklertools sind schwer zugänglich, die Konsole dagegen ist Text. Öffnen: Chrome Strg+Umschalt+J, Firefox Strg+Umschalt+K. 

    document.activeElement          // wo ist der Fokus gerade?
document.querySelectorAll('img:not([alt])').length   // Bilder ohne Alternativtext
[...document.querySelectorAll('h1,h2,h3')].map(h => h.tagName + ' ' + h.textContent.trim())

2023 – 2024 · Federated Information Systems

3. Lehrjahr: Rust und Abschlussprojekt

Im letzten Jahr habe ich mich eigenständig in Rust vertieft und mich in die Abteilungskomponente Samply.beam eingearbeitet, die Kommunikation in streng regulierten klinischen Netzwerken übernimmt. Mein Abschlussprojekt war eine Raumbelegungssoftware mit REST API, ORM-Mapper, Docker und dynamischem Frontend. 2024 habe ich die Ausbildung abgeschlossen.

Praxis-Tipps: Compiler, Container, Dokumentation

  • Rust-Compilermeldungen kurz halten Plattform: Linux und Windows

    Rusts Fehlermeldungen sind hervorragend, aber lang und voller ASCII-Pfeile. Für den schnellen Durchlauf gibt es ein Kurzformat mit einer Zeile pro Fehler: 

    cargo check --message-format short
cargo clippy --message-format short

    Erst wenn ein Fehler unklar ist, die ausführliche Meldung lesen – dann gezielt in eine Datei: cargo check 2> fehler.txt.

  • Logs eines einzelnen Containers verfolgen Plattform: Linux und Windows

    Die gemischten Logs aller Dienste sind nicht anhörbar. Immer einen Dienst und eine begrenzte Anzahl Zeilen wählen:

    docker compose logs --tail 20 -f api

    --tail 20 zeigt nur die letzten 20 Zeilen, -f liest neue Zeilen live mit.

  • Diagramme für die Projektdoku als Text schreiben Plattform: Linux und Windows

    Für die Projektdokumentation braucht man Diagramme. PlantUML beschreibt sie als Text – ich kann sie schreiben, im Git-Diff prüfen und sehende Prüfer bekommen trotzdem ein Bild. 

    @startuml
actor Nutzer
Nutzer -> Frontend : Raum buchen
Frontend -> API : POST /buchungen
API -> Datenbank : INSERT
API --> Frontend : 201 Created
@enduml

    Zur Kontrolle ohne Bild: Syntax prüfen, oder das Diagramm als Text rendern und lesen.

    plantuml -checkonly ablauf.puml
plantuml -tutxt ablauf.puml   # erzeugt ablauf.utxt

2024 – 2025

Entwickler und Administrator

Nach der Ausbildung bin ich als Entwickler in der Abteilung geblieben. Ich habe an secret-sync gearbeitet, einer Rust-Komponente, die das Anwendungs- und Nutzermanagement über Authentik und Keycloak automatisiert, und den Pseudonymisierungsdienst Mainzelliste über OAuth abgesichert.

Außerdem war ich für die Serveradministration und interne Dienste (Confluence, GitLab, Authentik) sowie für das Gruppenmanagement der Forschungspartner verantwortlich. Dazu kamen ein Java-Generator für synthetische FHIR-Testdaten, API-Dokumentation mit Swagger UI und eine plattformübergreifende Version der Raumbelegungssoftware mit Tauri.

Praxis-Tipps: Server und Betrieb

  • Fenrir: Screenreader für die Linux-Konsole Plattform: Linux

    Fenrir ist ein Screenreader für die Textkonsole (TTY), ganz ohne grafische Oberfläche. Das ist mein tägliches Werkzeug: schlank, schnell und unabhängig vom Desktop.

    • Mit dem Review-Modus liest du bereits ausgegebene Zeilen nach, ohne die Eingabe zu verlassen.
    • Es funktioniert auch, wenn der Desktop nicht startet – gerade bei Systemproblemen ein großer Vorteil.
    • Unter Windows übernimmt diese Rolle WSL im Windows Terminal mit NVDA.
  • Systemlogs gezielt statt komplett lesen Plattform: Linux 
    journalctl -u nginx -n 20 --no-pager   # letzte 20 Zeilen eines Dienstes
journalctl -p err -b --no-pager        # nur Fehler seit dem letzten Start
grep -i -c error app.log               # wie viele Fehler gibt es überhaupt?

    Warum: --no-pager verhindert, dass ich in einem Pager festhänge; die Begrenzung auf Dienst, Priorität und Zeilenzahl macht aus tausend Zeilen zwanzig relevante.

  • SSH-Kurznamen statt langer Adressen Plattform: Linux und Windows

    Weniger tippen heißt weniger Tippfehler, die man sich erst wieder anhören muss. In ~/.ssh/config (unter Windows %USERPROFILE%\.ssh\config):

    Host gitlab-server
    HostName gitlab.intern.example.org
    User admin
    IdentityFile ~/.ssh/id_ed25519

    Danach reicht ssh gitlab-server.

  • API-Dokumentation als Liste statt als Swagger-Oberfläche Plattform: Linux und Windows

    Swagger UI ist für Sehende gemacht. Die OpenAPI-Datei dahinter ist JSON und lässt sich in Sekunden durchsuchen:

    curl -s http://localhost:8080/v3/api-docs | jq -r '.paths | keys[]'

    Das liefert alle Endpunkte als Liste – eine Zeile pro Pfad.

Ich habe die technische Leitung für zwei Datenplattformen in der Krebsforschung übernommen:

Praxis-Tipps: Kubernetes, Editor, Architektur

  • kubectl: nur die Spalten, die du wirklich brauchst Plattform: Linux und Windows

    Die Standardtabellen von kubectl sind breit und voller Spalten, die man selten braucht. Besser:

    kubectl get pods -o name
kubectl get pods --no-headers -o custom-columns=NAME:.metadata.name,STATUS:.status.phase
kubectl logs deploy/api --tail=20
kubectl get events --sort-by=.lastTimestamp | tail -n 10

    Für kubectl describe gilt dasselbe wie bei Logs: in eine Datei oder durch less, dann mit Suche nach Events oder Error springen.

  • NeoVim für den Screenreader ruhig stellen Plattform: Linux und Windows

    Zeilennummern, Icons und eingeblendete Diagnosen sehen gut aus, werden aber bei jeder Zeile mitgelesen. In meiner Konfiguration (init.lua) schalte ich sie ab und hole mir Informationen gezielt, wenn ich sie brauche: 

    vim.opt.number = false
vim.opt.relativenumber = false
vim.opt.signcolumn = "no"
vim.diagnostic.config({ virtual_text = false, signs = false })
    • ]d / [d springt zur nächsten / vorigen Diagnose, Strg+W d zeigt die Meldung an (NeoVim 0.10+)
    • :lua vim.diagnostic.setqflist() und :copen listen alle Fehler untereinander
    • In Distributionen wie AstroNvim lassen sich Icons über icons_enabled abschalten
  • Architektur so dokumentieren, dass das ganze Team sie lesen kann Plattform: Linux und Windows

    Als technische Leitung muss ich Architektur erklären, nicht nur bauen. Ich halte jedes Diagramm als PlantUML im Repository, direkt neben dem Code, und schreibe zu jedem Diagramm zwei, drei Sätze Fließtext.

    • Diagramme liegen versioniert im Git und werden im Merge Request mit geprüft.
    • Der Begleittext ist die Alternative für alle, die das Bild nicht sehen – und hilft auch Sehenden beim Einstieg.
    • Eine Datei pro Sicht: Komponenten, Datenfluss, Deployment.

Seit 2026

DevOps und eigene Plattform

Heute liegt mein Schwerpunkt auf dem ganzen Weg vom Code zum laufenden System: Container, CI/CD mit GitHub und GitLab, Kubernetes (CKAD-zertifiziert), Helm, Azure und S3-Speicher.

All das habe ich in meinem eigenen Projekt zusammengeführt, dem Accessible Job Manager: eine Bewerbungsplattform für blinde und sehbehinderte Menschen, gebaut mit Spring Boot und Angular, betrieben auf Azure Container Apps und von Anfang an barrierefrei gedacht, nicht nachträglich. Eine Demo-Instanz ist online (Testzugang auf Anfrage).

Praxis-Tipps: barrierefrei bauen

  • Formulare, die Fehler wirklich ansagen Plattform: Linux und Windows

    Ein rot umrandetes Feld sagt dem Screenreader nichts. Im Accessible Job Manager ist jede Fehlermeldung mit ihrem Feld verbunden: 

    <label for="email">E-Mail</label>
<input id="email" type="email" autocomplete="email"
       aria-invalid="true" aria-describedby="email-fehler">
<p id="email-fehler">Bitte eine gültige E-Mail-Adresse eingeben.</p>
    • Nach dem Absenden den Fokus auf das erste fehlerhafte Feld setzen.
    • Erfolg oder Fehler zusätzlich über eine aria-live-Region ansagen.
    • Pflichtfelder im Label kennzeichnen, nicht nur mit einem Sternchen-Symbol.
  • Der Zwei-Minuten-Tastaturtest Plattform: Linux und Windows

    Maus weglegen und die eigene Anwendung nur mit der Tastatur bedienen:

    • Erreicht Tab jedes Bedienelement in sinnvoller Reihenfolge?
    • Ist immer sichtbar und hörbar, wo der Fokus steht?
    • Lassen sich Dialoge mit Esc schließen, und landet der Fokus danach wieder am Auslöser?
    • Gibt es irgendetwas, das nur bei Mauszeiger-Hover erscheint?

    Diese Seite ist übrigens selbst so gebaut: Filter, Karten und Kopier-Buttons funktionieren komplett mit der Tastatur.

  • KI-Assistent im Terminal: Text rein, Text raus Plattform: Linux und Windows

    Ich arbeite mit Claude Code im Terminal. Für mich ist das ideal, weil alles Text ist: keine Seitenleisten, keine Pop-ups. Was mir am meisten hilft:

    • Zusammenfassungen anfordern: „Fasse diesen Diff in drei Sätzen zusammen“ statt hundert Zeilen anzuhören.
    • Ausgaben umformen lassen, etwa eine breite Tabelle in eine Liste.
    • Erzeugten Code trotzdem selbst lesen und testen – die Verantwortung bleibt bei mir.
