2005 – 2015

Factory floor and university

My working life began in production. At the Daimler truck plant in Mannheim I trained as an industrial mechanic and earned my university entrance qualification alongside. After that I worked in engine machining, CNC tool management and the foundry. Then I studied in Aschaffenburg: industrial engineering first, then business administration and law.

What I took from production is something I still rely on: processes have to be reproducible, and a small mistake at the start of the chain gets expensive at the end. That is exactly how I think about builds, deployments and data pipelines today.

2

2015 – 2021

Losing my sight, starting over

In 2015 I lost my sight. The years that followed were about medical rehabilitation and the question of how to work without seeing: training in blindness skills, braille, and new routines for everyday life.

From 2020 to 2021 I completed vocational rehabilitation at QuikStep in Durmersheim. There I learned C and the fundamentals of computer science, and built a way of working entirely without visuals: screen reader, keyboard shortcuts, audio output and braille. That year it became clear to me: programming is text, and with text I can work at full speed.

Practical tips for getting started

  • Learn one screen reader properly, not three halfway Platform: Linux and Windows

    On Windows, NVDA is free and a good start; on a Linux desktop, Orca (toggled in GNOME with Super+Alt+S). The shortcuts worth learning first are almost the same everywhere on the web and in applications:

    • H next heading, D next region (landmark), F next form field, K next link
    • NVDA+F7 elements list: all headings, links and landmarks at a glance
    • NVDA+Space switches between browse and focus mode – the most common reason “the keys suddenly stopped working”

    Why: once you can navigate by structure, you are faster than anyone listening to a page line by line.

  • Raise the speech rate step by step Platform: Windows

    In NVDA, NVDA+Ctrl+Left/Right arrow moves through the synth settings ring (rate, pitch, volume …), and NVDA+Ctrl+Up/Down arrow changes the selected value.

    Increase the rate in small steps, every week or two, once the current speed feels normal. A high rate saves a lot of time every day when reading code and logs.

    Why: too fast too early means you rewind more than you read.

  • A braille display for code: the characters speech swallows Platform: Linux and Windows

    Speech is fast but imprecise for code: brackets, semicolons and indentation are easy to miss. A braille display with 8-dot computer braille shows every character exactly as it is in the file.

    • For overview and prose: speech
    • For the one line with the syntax error: braille
    • Set punctuation level to “all” for coding, so speech reads brackets too
  • First C programs: only ever read the first error Platform: Linux and Windows

    A single missing semicolon often causes twenty follow-up errors. With a screen reader that is especially tiring. Print only the first lines, fix, compile again. 

    gcc -Wall -Wextra -o hello hello.c 2>&1 | head -n 5

    The message starts with file:line:column. With the line number you jump straight there in the editor instead of searching.

2021 – 2022 · Apprenticeship at the DKFZ

Year 1: terminal, SQL and the fundamentals

At the German Cancer Research Center (DKFZ) in Heidelberg I started an inclusive apprenticeship as an IT specialist for application development; vocational school was the Hubert-Sternberg-Schule in Wiesloch. The first year in the Federated Information Systems department was about the fundamentals: distributed systems, medical informatics, Java, APIs, Docker, Linux configuration, Git, databases and Scrum.

This is where I learned that the terminal is not a workaround for blind developers but the most accessible tool there is – once you bring its output into a readable shape.

Practical tips: terminal and databases

  • Linux terminal: output in bites, not as a wall Platform: Linux

    Long output rushes past a screen reader. These patterns keep it readable:

    ls -1                      # one file per line
ls -1 | wc -l              # count first, then decide
command | head -n 20       # just the beginning
command | less             # page by page, with /search
command > output.txt 2>&1  # to a file, then read it in the editor
cd -                       # back to the previous directory

    Why: a file in the editor I can read line by line, search, and take my time with – scrolling output I cannot.

  • Make Windows Terminal and PowerShell readable Platform: Windows

    Windows Terminal works well with NVDA. Ctrl+Shift+F searches the output, and the NVDA review cursor (numpad 7 8 9) moves back line by line. PowerShell prints wide tables by default – a vertical list is much nicer for speech: 

    Get-ChildItem | Select-Object -ExpandProperty Name
Get-Process code | Format-List Name, Id, CPU
Get-Content .\app.log -Tail 20
Get-ChildItem | Out-File list.txt    # read it as a file
Get-Location | Set-Clipboard         # to the clipboard

    In the classic command prompt, dir /b prints names only.

  • SQL in the terminal: records stacked, not as a table Platform: Linux and Windows

    A wide result table is read out as “dash dash plus dash …”. All common command-line clients can print records as column = value instead, one below the other: 

    -- SQLite (sqlite3)
.headers on
.mode line
SELECT * FROM application LIMIT 3;

-- PostgreSQL (psql)
\x auto
\pset pager off
SELECT * FROM application LIMIT 3;

-- MySQL / MariaDB: end the query with \G instead of ;
SELECT * FROM application LIMIT 3\G

    For scripts and quick counts without borders and headers:

    psql -d app -A -t -F ';' -c "SELECT status, count(*) FROM application GROUP BY status"

    Why: always start with count(*) or LIMIT – listening to a thousand rows is not data analysis.

  • Git without a pager and with short output Platform: Linux and Windows

    Git opens logs and diffs in a pager that is often awkward to leave with a screen reader. Short formats help straight away: 

    git status -s
git --no-pager log --oneline -n 10
git diff --stat
git diff --word-diff   # shows which word changed, not just the line

    If you never want the pager: git config --global core.pager cat.

  • Trim Docker output to what matters Platform: Linux and Windows

    docker ps prints a very wide table. With --format you get exactly the fields you need:

    docker ps --format '{{.Names}}: {{.Status}}'

    Result, for example: db: Up 2 hours – one line per container, understood instantly.

2022 – 2023 · Cancer Information Service

Year 2: web development

In my second year I was at the Cancer Information Service (Krebsinformationsdienst), working with PHP and JavaScript on an online counselling platform. It was my first work on interfaces that other people use – and the best school for seeing accessibility from the other side.

Practical tips: web and APIs

  • Test your own pages with a screen reader in three steps Platform: Linux and Windows
    1. Headings: jump through them with H. Does the list alone make a sensible table of contents?
    2. Regions: move through landmarks with D. Are there header, nav, main, footer?
    3. Forms: Tab through every field. Is a label read for each one, not just “edit text”?

    Why: these three checks find most problems within minutes, long before an audit tool runs.

  • Read APIs with curl and jq instead of in the browser Platform: Linux and Windows

    JSON in the browser is often one long paragraph for a screen reader. In the terminal, jq formats the response and filters out exactly what you need: 

    curl -s https://api.example.org/jobs | jq '.'
curl -s https://api.example.org/jobs | jq -r '.items[].title'
curl -s https://api.example.org/jobs | jq '.items | length'

    On Windows, curl.exe and jq are available too, for example via winget install jqlang.jq.

  • The browser console instead of visual dev tools Platform: Linux and Windows

    The visual parts of developer tools are hard to use, but the console is text. Open it: Chrome Ctrl+Shift+J, Firefox Ctrl+Shift+K. 

    document.activeElement          // where is the focus right now?
document.querySelectorAll('img:not([alt])').length   // images without alt text
[...document.querySelectorAll('h1,h2,h3')].map(h => h.tagName + ' ' + h.textContent.trim())

2023 – 2024 · Federated Information Systems

Year 3: Rust and the final project

In my final year I taught myself Rust in depth and got into the department's Samply.beam component, which handles communication in strictly regulated clinical networks. My final project was a room booking application with a REST API, ORM mapper, Docker and a dynamic frontend. I qualified in 2024.

Practical tips: compiler, containers, documentation

  • Keep Rust compiler messages short Platform: Linux and Windows

    Rust's error messages are excellent, but long and full of ASCII arrows. For a quick pass there is a short format with one line per error: 

    cargo check --message-format short
cargo clippy --message-format short

    Only read the full message when an error is unclear – and then into a file: cargo check 2> errors.txt.

  • Follow the logs of a single container Platform: Linux and Windows

    The mixed logs of every service are impossible to listen to. Always pick one service and a limited number of lines:

    docker compose logs --tail 20 -f api

    --tail 20 shows only the last 20 lines, -f follows new lines live.

  • Write the project's diagrams as text Platform: Linux and Windows

    Project documentation needs diagrams. PlantUML describes them as text – I can write them, review them in a Git diff, and sighted examiners still get a picture. 

    @startuml
actor User
User -> Frontend : book room
Frontend -> API : POST /bookings
API -> Database : INSERT
API --> Frontend : 201 Created
@enduml

    To check without an image: validate the syntax, or render the diagram as text and read it.

    plantuml -checkonly flow.puml
plantuml -tutxt flow.puml   # creates flow.utxt

2024 – 2025

Developer and administrator

After the apprenticeship I stayed in the department as a developer. I worked on secret-sync, a Rust component that automates application and user management through Authentik and Keycloak, and secured the Mainzelliste pseudonymisation service with OAuth.

I was also responsible for server administration and internal services (Confluence, GitLab, Authentik) and for group management for our research partners. On top of that: a Java generator for synthetic FHIR test data, API documentation with Swagger UI, and a cross-platform version of the room booking software built with Tauri.

Practical tips: servers and operations

  • Fenrir: a screen reader for the Linux console Platform: Linux

    Fenrir is a screen reader for the text console (TTY), with no graphical desktop at all. It is my everyday tool: lean, fast and independent of the desktop.

    • Review mode lets you read lines that were already printed without leaving the prompt.
    • It works even when the desktop will not start – a big advantage exactly when something is broken.
    • On Windows, WSL in Windows Terminal with NVDA fills this role.
  • Read system logs selectively, not in full Platform: Linux 
    journalctl -u nginx -n 20 --no-pager   # last 20 lines of one service
journalctl -p err -b --no-pager        # only errors since the last boot
grep -i -c error app.log               # how many errors are there at all?

    Why: --no-pager stops me getting stuck in a pager; limiting by service, priority and line count turns a thousand lines into twenty relevant ones.

  • SSH aliases instead of long addresses Platform: Linux and Windows

    Less typing means fewer typos you have to listen back to. In ~/.ssh/config (on Windows %USERPROFILE%\.ssh\config):

    Host gitlab-server
    HostName gitlab.internal.example.org
    User admin
    IdentityFile ~/.ssh/id_ed25519

    After that, ssh gitlab-server is enough.

  • API docs as a list instead of the Swagger interface Platform: Linux and Windows

    Swagger UI is made for sighted users. The OpenAPI file behind it is JSON and can be searched in seconds:

    curl -s http://localhost:8080/v3/api-docs | jq -r '.paths | keys[]'

    That gives you every endpoint as a list – one line per path.

2025 – 2026

Technical lead

I took over as technical lead for two data platforms in cancer research:

  • ITCC Federated Data Hub – international integration of paediatric cancer data across clinical sites. Federated ingestion of FHIR and genetic data, pseudonymised central storage with S3 and Apache Iceberg, deployment on Kubernetes.
  • LeMeDart – a data hub with partners across Germany: central data intake from REDCap, pseudonymisation and storage.

I was responsible for architecture, backend services, data processing and deployment, and secured the Java-based Samply Exporter with multiple Spring Security filter chains and group-based authorisation via OIDC.

Practical tips: Kubernetes, editor, architecture

  • kubectl: only the columns you actually need Platform: Linux and Windows

    kubectl's default tables are wide and full of columns you rarely need. Better:

    kubectl get pods -o name
kubectl get pods --no-headers -o custom-columns=NAME:.metadata.name,STATUS:.status.phase
kubectl logs deploy/api --tail=20
kubectl get events --sort-by=.lastTimestamp | tail -n 10

    The same goes for kubectl describe as for logs: into a file or through less, then search for Events or Error.

  • Quieten NeoVim for the screen reader Platform: Linux and Windows

    Line numbers, icons and inline diagnostics look nice but get read out with every line. In my configuration (init.lua) I turn them off and fetch information on demand: 

    vim.opt.number = false
vim.opt.relativenumber = false
vim.opt.signcolumn = "no"
vim.diagnostic.config({ virtual_text = false, signs = false })
    • ]d / [d jumps to the next / previous diagnostic, Ctrl+W d shows the message (NeoVim 0.10+)
    • :lua vim.diagnostic.setqflist() and :copen list all errors one below the other
    • In distributions such as AstroNvim, icons can be turned off via icons_enabled
  • Document architecture so the whole team can read it Platform: Linux and Windows

    As technical lead I have to explain architecture, not just build it. I keep every diagram as PlantUML in the repository, right next to the code, and write two or three sentences of prose for each.

    • Diagrams are versioned in Git and reviewed in the merge request.
    • The prose is the alternative for everyone who cannot see the image – and helps sighted readers get started too.
    • One file per view: components, data flow, deployment.

Since 2026

DevOps and my own platform

Today my focus is the whole path from code to running system: containers, CI/CD with GitHub and GitLab, Kubernetes (CKAD certified), Helm, Azure and S3 storage.

I brought all of it together in my own project, the Accessible Job Manager: a job application platform for blind and visually impaired people, built with Spring Boot and Angular, running on Azure Container Apps and designed to be accessible from the start rather than retrofitted. A demo instance is online (test access on request).

Practical tips: building accessibly

  • Forms that actually announce their errors Platform: Linux and Windows

    A red border tells a screen reader nothing. In the Accessible Job Manager every error message is linked to its field: 

    <label for="email">Email</label>
<input id="email" type="email" autocomplete="email"
       aria-invalid="true" aria-describedby="email-error">
<p id="email-error">Please enter a valid email address.</p>
    • After submitting, move focus to the first invalid field.
    • Also announce success or failure through an aria-live region.
    • Mark required fields in the label text, not only with an asterisk.
  • The two-minute keyboard test Platform: Linux and Windows

    Put the mouse away and use your application with the keyboard only:

    • Does Tab reach every control in a sensible order?
    • Is it always visible and audible where the focus is?
    • Do dialogs close with Esc, and does focus return to the button that opened them?
    • Is there anything that only appears on mouse hover?

    This page is built that way too: filter, cards and copy buttons all work entirely with the keyboard.

  • An AI assistant in the terminal: text in, text out Platform: Linux and Windows

    I work with Claude Code in the terminal. For me that is ideal, because everything is text: no sidebars, no pop-ups. What helps me most:

    • Ask for summaries: “Summarise this diff in three sentences” instead of listening to a hundred lines.
    • Have output reshaped, for example a wide table into a list.
    • Still read and test generated code myself – the responsibility stays with me.
